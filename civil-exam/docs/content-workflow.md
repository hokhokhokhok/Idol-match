# 문항 세트 제작·검수 흐름 (7단계)

세트 하나 = `src/data/sets/<세트id>.json` 파일 하나(문항 40개 배열). 파일을 넣고 빌드하면 홈 화면에 세트가 나타난다.

```
① 생성 (Claude 세션)  →  ② npm run validate -- --strict  →  ③ 검수 시트로 사람이 검수  →  ④ npm run mark  →  ⑤ 빌드·배포
```

## ① 생성

새 세션에서 아래 요청문을 붙여 넣는다. `<…>`만 바꾼다.

> civil-exam/docs/content-workflow.md 의 "작성 규칙"을 지켜 `civil-exam/src/data/sets/<2026-002>.json` 에 40문항 세트를 만들어줘.
> 이전 세트에서 다룬 쟁점(아래 "쟁점 사용 현황")과 겹치지 않게 하고, 끝나면 `npm run validate -- --strict <파일>` 을 통과시키고,
> `npm run review-sheet -- <2026-002>` 로 검수 시트를 만든 뒤 쟁점 사용 현황 표를 갱신해줘.

### 작성 규칙

- **창작 문항만.** 기출·학원 모의고사·공단 문항의 문장을 옮기지 않는다. 출제 경향(쟁점, 지문 길이, 보기 구성)만 따른다. `source: "original"`.
- **출제범위·배분** (`config/exam.json`, `config/blueprint.json`): 민법 **총칙·물권만**. 총칙 20 · 물권 20, 단원 안의 쟁점 배분도 blueprint를 따른다. 문항 번호는 총칙(1~20) → 물권(21~40) 순. `unit`은 `총칙`·`물권`(·`기타`)만 쓸 수 있다(그 밖은 검증 오류).
- **유형**: 단일 정답형(옳은/옳지 않은 것) 약 55%, 조합형(ㄱㄴㄷㄹ)·개수형 약 30%, 사례형(갑·을·병) 약 15%. 판례형은 단일형 안에서 섞는다.
- **정답 번호**: ①~⑤가 각 8개 안팎 (검증 스크립트가 ±3 넘으면 경고).
- **정답은 하나뿐**: 각 보기를 "옳다/틀리다" 중 하나로 단정할 수 있게 쓴다. 판례에 예외가 있는 쟁점은 "원칙적으로", "특별한 사정이 없는 한"을 넣어 다툼 여지를 없앤다. 요건을 나열하는 보기는 요건을 빠뜨리면 틀린 지문이 되므로 범위를 좁혀 쓴다.
- **분량** (기획안 7절, `npm run validate`가 검사): 단일형 발문 20~40자·보기 50~120자·전체 300~650자 / 조합형 박스 항목 60~130자·전체 400~700자 / 사례형 사실관계 200~380자·보기 50~130자·전체 550~900자 / 판례형 발문 20~40자·보기 60~130자·전체 350~650자.
- **문체**: "~한다.", "~할 수 없다." 본문에는 조문 번호를 쓰지 않고(시험지처럼), **해설에만** "제OOO조"를 적는다. 판례가 쟁점이면 발문 끝에 "(다툼이 있는 경우 판례에 따름)".
- **해설**: `summary` 핵심 한 줄, `perChoice` 5개는 각 보기가 옳은/틀린 이유와 조문(조합형은 ㄱ~ㄹ 판단을 정답 보기 해설에 모은다). `statutes`는 "민법 제OOO조" 형식.
- **판례**: 사건번호·선고일은 쓰지 않는다(AI가 틀리게 만들 수 있음). `cases[].gist`에 "~라는 취지"로 판례 취지만 적고 `verified: false`. 사용자가 확인한 뒤에만 `citation`과 `verified: true`를 넣는다.
- **현행법 기준**: 개정이 최근에 있었거나 개정 논의 중인 조문(최근 개정된 조문 등)은 출제를 피하거나, 출제 전 국가법령정보센터에서 현행 조문을 확인한다.
- `reviewed: false`로 둔다(검수는 사람이 한다).

## ② 자동 검증

```bash
npm run validate -- --strict src/data/sets/<세트id>.json
```

오류(✗)는 반드시 고친다. 경고(△)도 새 세트는 0개를 목표로 한다(`--strict`). 참고(·)의 미검수·판례 미확인은 ③에서 줄여 간다.

## ③ 검수 (사람)

```bash
npm run review-sheet -- <세트id>     # docs/review/<세트id>.md 생성 — 휴대폰·아이패드로 읽기 좋다
```

문항마다 확인:

1. 정답이 하나뿐인가 — 다른 보기도 옳다(또는 틀리다)고 다툴 여지가 없는가
2. 보기별 해설의 옳고 그름이 정답과 맞는가, 조합형이면 ㄱ~ㄹ 판단이 정답 조합과 맞는가
3. 근거 조문을 [국가법령정보센터](https://www.law.go.kr) 현행 민법과 대조
4. 판례 취지를 [대법원 종합법률정보](https://glaw.scourt.go.kr)에서 확인 — 사건번호를 찾으면 기록

문제가 있으면 JSON을 직접 고치거나, Claude 세션에 "2026-001-q07 보기 ③이 ○○ 판례와 다르니 고쳐줘"처럼 요청한다.

## ④ 검수 표시

```bash
npm run mark -- 2026-001-q01 2026-001-q02                       # 검수 완료 (앱의 '미검수' 배지가 사라짐)
npm run mark -- 2026-001-q01 --case 1 --citation "대법원 ○○○○. ○. ○. 선고 ○○다○○○○ 판결"   # 판례 확인 (해설의 '판례 확인 필요' 배지가 사라짐)
npm run mark -- 2026-001-q01 --undo                             # 되돌리기
npm run review-sheet -- 2026-001                                 # 진행 상황 다시 보기
```

`mark`는 저장 전에 검증을 다시 돌려 오류가 있으면 저장하지 않는다.

## ⑤ 반영

```bash
npm test && npm run build && npm run test:e2e
```

커밋·배포하면 아이패드 앱은 다음 실행 때 새 세트를 받는다. 이미 푼 기록·오답노트는 문항 id로 연결되므로 **배포한 세트의 문항 id는 바꾸지 않는다**(내용 수정은 괜찮다).
